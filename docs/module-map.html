      系統架構：誰做決策，誰執行

      這是同一個 Python package 內的模組分工。箭頭代表呼叫方向；操作層、確定性資料管線、追蹤與通訊保持不同職責。

      位置負責的決策／工作呼叫下一步不自行處理
      入口
      web/app.py · cli.py      		解析 HTTP 表單、登入 session 或 CLI 參數；把結果呈現給人。系辦頁面：工作總覽（含人工關卡）、匯入資料、文件中心、通訊記錄、委員個資、期限設定。呼叫 application 的操作函式。不在路由或 CLI 重新實作期限、版本、缺件、放行或產檔規則。
      操作層
      application.py      		把一次動作組成用例：保存學生填寫、依時段決定能否送出、選建檔或產檔階段、人工關卡放行、讀寫追蹤狀態、安排草稿與委員個資索取。呼叫 workflow、engines、scheduler、mail、settings、case_review、committee_requests。不自己解析 Excel、計算清冊儲存格或實作 SMTP。
      確定性資料管線
      workflow.py      		讀附件2 與學生填寫、疊加委員回填、整合委員與費用、檢核案件、保存主檔；按階段產附件 4／6。呼叫 ingest、registry、validation、master、generators。不判斷誰登入、何時催件、案件是否放行或是否寄信。
      追蹤
      engines/ · scheduler.py · issue_store.py      		由主檔與上一輪狀態得出缺件、教授確認、附件回收及到期提醒；缺件逐筆的生命週期。state.py 保存快照；drafts.py 組提醒草稿。不把「排了一封提醒」當成真的已寄出。
      通訊
      mail/notify.py · send_log.py      		對學生責任問題組補件信、對委員組個資索取信；按追蹤鍵去重、呼叫寄送器並記結果。正式送信可由 email_sender.py 呼叫 SMTP。不自行建立案件或把寄送成功推定成對方已回覆。

      資料走向：來源、快照、狀態與產物不能混為一談

      附件2 是案件來源；學生填寫只補附件 3 資料；主檔是可重建的業務快照；追蹤狀態是跨批次的工作紀錄。它們即使包含相同案件鍵，也有不同的寫入者與生命週期。

      操作層到底做什麼？

      它負責決定與協調

      • 先驗證學生 Email、委員 E-mail、指導教授、委員人數／單位與口試日期，再保存填寫並歸檔舊版；另回傳不阻擋的自我檢查提示。
      • 固定使用系辦設定的本期學期；決定案件只來自附件2，學生填寫只補資料，配不上的列例外。
      • 依時段執行每日自動化：填寫期間只建預覽；補件期間正式檢核寄信；截止後鎖定。
      • 人工關卡：列出每案例外、要求處理人姓名並寫入稽核；產檔與委員個資索取都只處理已放行案件。

      它交給既有模組執行

      • ingest / registry / model 解析來源、建立案件與委員身分、疊加回填、沿用舊口委。
      • validation / workflow / generators 檢查資格（含委員職級）並產主檔、附件 4／6。
      • engines / scheduler / issue_store 計算缺件、教授確認、回收及催辦。
      • mail / send_log 組信、去重並記錄寄送結果。

      缺件的完整生命週期：issue_store.py 六態狀態機

      在 engines/deficiency.py 的粗粒度 new／notified／overdue 之上，issue_store.py 記錄每筆缺件從偵測到解決的每一步；不可跳步，復發時可從 resolved 回到 detected。對帳、補件信寄送與學生重送都會推進這些狀態，系辦案件抽屜的「缺件進度」時間軸即讀此紀錄。

      狀態說明與觸發
      detected系統重建 Master 並重跑 validation 後，首次發現該筆缺件。
      draft_ready補件信草稿已產生。
      request_sent補件信已寄出（經 send_log 記錄）。
      resubmitted學生重新送出；此後不再收到「尚未提交」催件。
      revalidated系統重建 Master 後重跑 validation。
      resolved該欄位通過驗證，問題解除。
      revalidated → request_sent複驗仍未通過，退回再通知一輪（不是新狀態，是回退路徑）。
      resolved → detected同一追蹤鍵復發，強制轉回 detected 重新追蹤（不是新狀態，是回退路徑）。

      已實作與尚未閉合的地方

      學生入口等待 Portal 端確認

      學生如何登入、驗證身分，須等 Portal 端可提供的能力確定後再決定。現有網頁只輸入學號即可進入，是開發原型，正式環境不可沿用。

      教授回信判讀尚未接 LLM

      每日自動化已把附件4（全學期一份，2026-10-10 起）寄給名下案件全部放行的指導教授（advisor_confirmation.py，每位收到同一份、信中只列自己學生；自己的列變動才重寄給本人），automate --send 會以 IMAP 讀回信、核對寄件者與版本後放進文件中心「教授回信待判讀」。LLM 判讀尚未接上，目前由系辦判讀「確認無誤／需修改／忽略」；逾期催辦信主旨沒有代碼，回信只能依寄件者唯一對應。接法與護欄見 LLM 前置研究。

      委員個資回覆管道

      索取信附委員專屬連結（/committee/reply/<代碼>，需設定 KOUSHI_PUBLIC_URL），委員線上填寫；改以回信提供者由系辦在「委員個資」頁登錄。正式上線須 HTTPS，個資存檔加密日後處理。委員未回覆的催件參數尚未定；口試前 3 天（暫定常數）仍未回填即列為人工關卡例外。

      人工關卡的時間與重審

      放行未強制在補件截止日之前；放行後委員名單變動或出現放行時沒有的新例外，都只標示、不自動撤銷（是否重審待決）。

      費用規則仍需系辦確認

      口試費目前暫以每位委員在同一清冊場次套用「碩 3／博 6」上限；本校他系是否免撥帳與交通費、指導教授兼任委員是否支領口試費都保留為設定，預設不改原行為。

      版本範圍

      教授確認已綁附件4 內容版本（由系統寄出者）：內容變動即重設重寄；系辦手動登錄「已寄出」的請求沒有版本可比。附件6 回收仍按清冊鍵對帳，換委員或改金額但案件鍵不變時，舊回收紀錄可能被沿用。

      批次與併行

      建檔區段有 OS 層級排他鎖；主檔、Registry 與附件仍分別寫入，尚無 staging＋manifest 的整批原子發布。

      其他系所

      目前以本系規定為準（委員名單與 E-mail 必填、職級規則）；其他系所（Portal 委員欄非必填等）納入時需調整。

      同一案件每次重新送出遞增的整數；用於寄信去重，尚不等於附件內容版本。
      時段 phase
      依系辦設定的填寫截止日與補件截止日劃分：填寫期間、補件期間、補件已截止；決定學生能否送出與自動化做什麼。
      資料異常 issue
      解析或檢核後的問題，含案件、欄位、責任與附件4／6 阻擋資訊；系辦責任者即人工關卡的「例外」。
