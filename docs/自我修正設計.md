# 自我修正設計（有界的觀察 → 檢核 → 修正）

對應競賽辦法第三條第 3 款「狀態管理與動態調整：能依中間結果、錯誤、環境變化或使用者回饋修正計畫、重試、改用替代工具或中止任務」，以及決賽「Agentic 技術深度與適切性」。

## 一、為什麼要做

原本每個 agent 的模型輸出一旦沒通過程式檢核，就直接整件轉人工。這很安全，但浪費了一次「模型其實只差一點」的機會。例如：引用時多改了一個字、候選代號打錯、級別寫成清單外的詞。這類錯誤只要把原因告訴模型，通常就能改對。

本設計讓 agent 依中間結果調整，但**不放寬任何安全條件**：
- 修正後的輸出走同一道檢核、同一個政策閘門。
- 次數有上限，不會無限重試。
- 修正失敗照舊轉人工。
- 每一次嘗試都寫進軌跡，評審可以逐步查核。

## 二、四層機制

| 層 | 觸發條件 | 動作 | 上限 | 模組 |
|---|---|---|---|---|
| 1. 輸出修正 | 模型輸出未通過檢核（不是 JSON、缺欄位、類別或級別不在白名單、候選代號不存在、依據或修改內容不是原信逐字引用） | 把檢核原因回饋給模型重新輸出 | 每次呼叫 1 次 | `koushi/agent_loop.py` `complete_validated()`；信箱 agent、三個提案型 agent |
| 2. 重新規劃 | 教授要求的修改對不上可修正欄位（看不懂的日期、時間、口試方式，或無法對應欄位） | 把那幾筆連同允許欄位與格式交回模型重新整理；整理後仍要對得上欄位 | 每封信 1 次 | `mailbox_agent._replan_modifications()` |
| 3. 回答反思 | 問答助理的回答沒通過 grounding check（數字、代號、狀態沒有工具結果佐證） | 告訴模型哪些內容沒有根據，讓它補查工具或改寫 | 每個問題 1 次 | `assistant.ask()`（`MAX_REFLECTIONS`） |
| 4. 連線重試與備援 | API 逾時（15 秒）、429、5xx | 兩家金鑰都有設定時：主要供應商失敗立刻改用另一家，不重試，且 5 分鐘內直接用備援（畫面最多等一次逾時）；只有一家時：依建議等待時間重試 1 次（建議超過 5 秒或每日免費額度用完則不等，轉人工） | 每次呼叫最多 1 次重試（無備援）或 1 次備援 | `koushi/llm.py` `ResilientLLM` |

刻意**不**修正的情況：
- **白名單外的動作**（例如模型自己發明「確認附件4」）：直接丟棄，不請模型「修成合法動作」，避免它換一個動作繞過政策。
- **換委員、找不到是哪位學生或委員**：依政策或身分本來就該人工處理，不重新規劃。
- **金鑰錯誤、參數錯誤**：重試同一家沒有用，直接改用備援；沒有備援就轉人工。
- **模型有回應但內容壞掉**：交給第 1 層請模型修正，不換供應商。

## 三、安全設計

1. **同一道檢核**：修正後的輸出走同一個 `validate`，政策閘門（`decide_policy`）完全不變。修正過的修改項目一樣是「草稿待核准」。
2. **有上限**：每次呼叫最多修正一次，重新規劃和反思各一次，連線重試或備援一次。上限寫在程式常數裡，測試會鎖住。
3. **回饋不擴大個資範圍**：回饋不加入任何新的原始資料。模型上一次的輸出要先清理才送回（遮掉信箱、身分證、8 碼以上數字）。被誘導的模型可能在輸出裡夾帶系統刻意沒送的內容，例如引用串裡的指令或外部信箱；評測的 INJ08、INJ-CO01 就是在開發這個功能時抓到這個問題。所以**信箱 agent 完全不回送上一次輸出**，只回饋檢核原因。
4. **不會比原本更差**：信箱 agent 修正後如果仍有個別項目引用不合格，就退回原本的寬鬆結果（丟掉那幾筆、保留其餘）。
5. **AI 總開關優先**：總開關關閉時不建立模型，四層都不會發生。

## 四、軌跡

| 步驟 | agent | decision |
|---|---|---|
| `validate` | 信箱 | `pass`／`repair`（將修正）／`partial`（修正後仍有項目不合格，保留其餘）／`fail` |
| `replan` | 信箱 | `pass`／`fail` |
| `llm_call` | 提案型 | `pass`／`repair`／`fail` |
| `grounding_check`、`reflect` | 問答助理 | `pass`／`repair`／`fail` |

`analyze` 步驟的輸出多了 `attempts`（嘗試次數）與 `repaired`（是否經過修正）。「Agent 指標」頁和評測報告新增兩項指標：「自我修正次數」與「修正成功率」（有觸發修正的任務中，修正後不必轉人工的比例）。

## 五、驗證

- 單元測試：`tests/test_agent_loop.py`（修正上限、回饋清理、部分接受；連線重試、備援、金鑰錯誤不重試、內容錯誤不換供應商）。
- 各 agent 測試：
  - 信箱 agent：`tests/test_mailbox_agent.py` 第 9 節，涵蓋逐字引用修正、上限、部分接受、不修正白名單外動作、重新規劃、換委員不重新規劃，以及指標。
  - 提案型 agent：`tests/test_proposal_agents.py`。
  - 問答助理：`tests/test_assistant.py`（反思）。
- 評測：`eval/run_agent_eval.py` 新增 `repair` 模式。模型第一次輸出一定不合格，看到回饋後才答對，預期結果與 oracle 相同。見 [eval/README.md](../eval/README.md)。
- 示範：`python -m show --agents` 步驟 11e 會顯示「第 1 次判讀未通過檢核 → 回饋 → 第 2 次通過」。

## 六、成本與延遲

修正只在檢核失敗時才發生。最壞情況下每封信的模型呼叫次數：分析 2 次、重新規劃 1 次，連線失敗時再加 1 次重試和 1 次備援。實際比例要看真實模型的評測結果；指標頁的「自我修正次數」可以直接看到。
