# 技術文件

口試行政系統的架構、Agentic 層、安裝執行、設定、權限與已知限制。依競賽決賽繳件要求（README／技術文件須涵蓋架構、安裝與執行、相依套件、模型與版本、API、環境變數、授權、資料流程、權限、已知限制、故障排除）整理。業務規則以[已確認流程決策](已確認流程決策.md)為準。

## 一、系統定位

系辦每學期處理研究生學位口試：Portal 匯出附件2 建檔 → 學生補填口試資料 → 檢核與補件 → 資料齊全即寄附件4 給指導教授參考（不用回信）→ 專員放行 → 向委員索取撥款個資 → 口試後產附件6 清冊並回收。

系統分兩層：

| 層 | 性質 | 內容 |
|---|---|---|
| 規則流程（既有） | 確定性 | 建檔、檢核、補件通知、催件、產檔、寄送去重、封存。期限與發送時刻由系辦設定。 |
| Agentic 層（本次新增） | LLM 提案＋確定性政策閘門＋人工核准 | 信箱 agent、回信處理 agent、提案型 agent（服務單位對應、來源異常修正、職稱判讀）、問答助理、統一執行軌跡、AI 總開關、評審模式、離線備援 |

原則：**模型只提案，不做決定**。每個 agent 的輸出先經程式驗證（schema、逐字引用、動作白名單、grounding check），再由政策決定能自動做多少；涉及財務（交通費、口試費）、資格、個資、案件狀態的動作一律要專員核准並記錄處理人。

## 二、架構

```
                 ┌──────────── 系辦網頁（Flask, koushi/web/app.py）────────────┐
                 │ 工作總覽 案件 期限設定 信箱 agent  AI 建議  問答助理  評審寄件匣 │
                 └───────┬───────────────┬───────────────┬────────────────────┘
                         │               │               │
   每日排程 automate ──► application.run_daily_automation（規則流程）
                         │     建檔 → 補件 → 催件 → 委員個資 → 附件4 確認
                         │     └─► 讀信箱（IMAP）→ 回信判讀 → 信箱 agent
                         │     └─►（釋放狀態鎖後）提案型 agent：服務單位／來源異常／職稱
                         │
        ┌────────────────┼──────────────────────────┐
        │ Agentic 層     │                          │
        │ mailbox_agent  reply_agent  affiliation/correction/title_agent  assistant
        │      │              │                │                         │
        │      └──── koushi/llm.py（StructuredLLM：Gemini／OpenAI／離線備援）
        │      └──── koushi/agent_trace.py（每一步寫入 audit_log.json）
        │      └──── koushi/ai_switch.py（緊急停止，優先於一切）
        └───────────────────────────────────────────┘
   資料：KOUSHI_DATA_ROOT（來源）、KOUSHI_OUTPUT_ROOT（主檔、狀態、產檔、封存）
```

互動式模組關係圖見 [module-map.html](module-map.html)。

### AI 在主畫面

agent 不只在側邊頁面：系辦每天打開的兩個主畫面都直接顯示 agent 的工作（`koushi/ai_digest.py`，唯讀、不呼叫模型）。

| 畫面 | 內容 |
|---|---|
| 工作總覽「AI 今日動態／待你決定」 | 待你決定：信件草稿待核准、來信待專員處理、AI 建議待決定（分 agent、標出模型失敗）；今日動態：信箱 agent 分析的來信（依分類）、自動完成、新增 AI 建議、自我修正的任務數、模型失敗轉人工。每列連到篩選好的信箱 agent／AI 建議／Agent 軌跡頁；標示目前模型、AI 總開關狀態與每日自動化最近一次執行時間。「今日」依系統時鐘（展示環境為模擬日期）。 |
| 案件頁「AI 協作（本案）」 | 已驗證連到本案的來信（寄件者身分、分類、摘要、建議動作與政策標示、處理狀態），以及與本案欄位、委員服務單位或職稱有關的待決 AI 建議；各附「到信箱 agent 處理」「到 AI 建議頁決定」與「查看完整軌跡」連結。核准與套用仍在原頁面進行（沿用既有 CSRF、處理人必填與評審白名單），案件頁不新增寫入操作。顯示前一律遮 8 碼以上數字與電子郵件帳號；寄件者不明、只在信中提到學號的來信不列。 |

### Agent 一覽

| Agent | 模組 | 目標與步驟 | 工具 | 不能做的事 | 設計文件 |
|---|---|---|---|---|---|
| 信箱 agent | `koushi/mailbox_agent.py` | 每封來信：解析 → 辨識寄件者 → 連結案件 → 個資防護 → 模型分析 → 規劃動作 → 政策決定 → 執行或待核 | 信件解析、寄件者比對、案件比對、修正層、範本回信 | 不能記錄「已確認」、不能改委員名單、不能自由文字回信 | [信箱agent設計](信箱agent設計.md) |
| 回信處理 agent | `koushi/reply_agent.py` | 教授要求修改 → 對應到欄位 → 修改前後對照與回信草稿 → 專員核准後寫入 → 重寄新版附件4 | 修正層 | 未核准不寫入 | 同上 |
| 服務單位對應 | `koushi/affiliation_agent.py` | （每日自動化或 AI 建議頁觸發）委員單位查不到距離 → 規則比對 → 候選前 8 名交模型排序 → 專員核准後寫進對照表 | 距離表檢索 | 未核准前交通費維持「找不到距離」 | [提案型agent設計](提案型agent設計.md) |
| 來源異常修正 | `koushi/correction_agent.py` | 附件2 欄位異常 → 模型提出修改 → 專員套用時走既有修正流程 | 修正層 | 只能改日期、時間、地點、出席方式、題目、職稱與單位 | 同上 |
| 職稱判讀 | `koushi/title_agent.py` | 規則判斷不了的職稱 → 模型判讀級別 | — | 不改變委員資格判定 | 同上 |
| 問答助理 | `koushi/assistant.py`、`assistant_tools.py` | 系辦提問 → 模型選唯讀工具 → 執行 → 作答 → grounding check | `overview_counts`、`list_cases`、`get_case`、`list_confirmations`、`list_deficiencies`、`list_source_issues`、`list_committee_data` 等唯讀工具 | 沒有任何寫入工具；姓名、學號以代號送模型 | [問答助理設計](問答助理設計.md) |

回信判讀分類器（`koushi/classifier.py`、`koushi/adapters/openai_adapter.py`）為既有功能：判讀教授回信是否為無保留確認，搭配白名單與自動確認規則（2026-10-12 起教授不用回信，此判讀只做紀錄）。

**附件4 寄送（2026-10-10 起全學期一份；2026-10-12 起不用回信）**：`advisor_confirmation.write_term_document()` 每學期產一份附件4（官方範本同一張表；檔案與全文件版本記在 `state/attachment4_documents.json`）。寄送請求是「學期＋指導教授」一筆（`engines/confirmation.create_requests`，共同指導的案件算在每位名下），教授名下學生資料全部齊全就寄、不等放行；每位教授附同一份檔案，信件內文只列他自己學生的列（姓名、學位、日期時間地點、委員），說明資料供參考、有錯再回信。教授不用回信，不催、不算逾期、不擋附件6。是否重寄所用的版本（`content_version`）只由這位教授自己的列計算，所以別位教授的變動不會重寄給他；自己的列變動只重寄給本人。教授回信要求修改時由回信處理 agent 擬修改，專員核准後寫入並重寄。

### 對照競賽門檻（第三條）

| 款 | 本系統 |
|---|---|
| 1 目標導向與任務分解 | 信箱 agent 每封信 8 個有依賴的步驟；回信處理 agent 從修改要求到重寄確認 |
| 2 工具或外部系統調用 | IMAP／SMTP、距離表、主檔、修正層；問答助理自選唯讀工具 |
| 3 狀態管理與動態調整 | 案件狀態機；**有界自我修正**（輸出未通過檢核就回饋原因重來一次、修改對不上欄位就重新規劃、回答沒根據就反思補查；見[自我修正設計](自我修正設計.md)）；連線失敗退避重試、改用備援模型；模型失敗逐封轉人工；疑似注入降級；版本變動重寄重確認；確認後不再問模型 |
| 4 權限與風險控制 | 政策閘門、專員核准、處理人紀錄、grounding check、個資不送模型、AI 總開關、評審模式權限白名單 |

## 三、安裝與執行

需求：Windows、Python 3.14（`requirements.txt` 為本機驗證過的完整相依清單）。附件4 舊式 `.doc` 範本轉檔需 LibreOffice（`KOUSHI_SOFFICE` 指定 `soffice.com`）。官方附件4／附件6 範本含真實資料，不進版控，需另行放到 `resource/template/`。

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m pytest -q          # 全部用合成資料、假寄送器、假 LLM
```

| 用途 | 指令 |
|---|---|
| 終端機展示（16 步，預設離線備援模型） | `python -m show`；只看 agent 段落 `python -m show --agents`；用真模型 `--live` |
| 網頁展示（假資料情境） | `powershell -File deploy\start-demo.ps1`，見模擬展示操作與驗收 |
| 評審模式 | `python -m koushi.demo judge [--offline]`（沒有金鑰時自動用離線備援），見[評審模式](評審模式.md) |
| 正式網頁 | `powershell -File deploy\start-web.ps1` |
| 每日自動化 | `powershell -File deploy\run-automation.ps1 -Preview`（預覽）；CLI `python -m koushi automate [--send]`。`--send` 時（有模型）規則流程與信箱 agent 之後接著跑三個提案型 agent，終端機印出新增的 AI 建議數；預覽模式不呼叫模型 |
| 只跑信箱 agent | `python -m koushi mailbox [--send]` |
| 評測 | 見 [eval/README.md](../eval/README.md) |

寄信預設只產草稿，加 `--send` 才寄出；網頁與排程的發送時刻由系辦在「期限設定」設定。

## 四、模型與 API

| 項目 | 內容 |
|---|---|
| 介面 | `koushi/llm.py` 的 `StructuredLLM.complete_json(system, user, schema_name) -> dict`；JSON mode、temperature 0 |
| 供應商 | Gemini（主要，`gemini-3.5-flash-lite`，經 OpenAI 相容端點；免費額度限速每次呼叫間隔 4 秒，`KOUSHI_LLM_MIN_INTERVAL` 可調）；OpenAI（也實測過的備選，預設 `gpt-4o-mini`）；離線備援 `offline-replay`（`koushi/offline_llm.py`，關鍵字規則替身，不連網，輸出標示「離線備援」） |
| 選擇順序 | AI 總開關關閉 → 不建立任何模型；`KOUSHI_LLM_PROVIDER=offline` → 離線備援；`KOUSHI_LLM_PROVIDER=openai` 且有 `OPENAI_API_KEY` → OpenAI 為主、Gemini 備援（決賽展示用：gpt-4o-mini 實測平均 1–2 秒，不需免費額度限速）；`KOUSHI_LLM_PROVIDER=ollama` → 本機 Ollama 模型（預設 `qwen2.5:3b`，OpenAI 相容端點 `http://localhost:11434/v1`，不連外網、不需金鑰、不改用雲端備援）；有 `GEMINI_API_KEY` → Gemini；有 `OPENAI_API_KEY` → OpenAI（`OPENAI_BASE_URL` 可指向相容端點）；都沒有 → None，所有 agent 轉人工 |
| Prompt 版本 | 回信判讀 `v1.2`；信箱 `mailbox-v1.1`；服務單位 `affiliation-v1`；來源異常 `correction-v1`；職稱 `title-v1`；問答助理 `assistant-v1`。每一步軌跡記錄 model 與 prompt_version |
| 用量 | 每次呼叫記錄 prompt／completion tokens，寫進軌跡供成本統計 |
| 重試與備援 | `ResilientLLM`：單次呼叫逾時 15 秒（`KOUSHI_LLM_TIMEOUT` 可改）。兩家金鑰都有設定時（Gemini 為主、OpenAI 備援），主要供應商失敗**不重試、立刻改用備援**，並在 5 分鐘內直接用備援，最壞只等一次逾時；只有一家時，逾時、429、5xx 重試一次（建議等待超過 5 秒或每日額度用完則不等，直接轉人工）；金鑰錯誤不重試同一家 |
| 自我修正 | `koushi/agent_loop.py`：輸出未通過檢核就把原因回饋給模型重來，每次呼叫最多一次；回饋前先清理，信箱 agent 不回送上一次輸出（[自我修正設計](自我修正設計.md)） |

## 六、資料流程與個資

- 案件唯一來源是 Portal 匯出的附件2；學生在系統補填口試日期、教授、委員與信箱；委員個資由本人經一次性連結回填或系辦登錄。
- **送模型前**：身分證、帳號、地址不送；信件內容出現身分證號或連續 10 位以上數字時整封不送；問答助理把姓名、學號換成代號，回答後再換回；軌跡的輸入摘要再遮一次 8 碼以上數字。
- 所有狀態寫在 `KOUSHI_OUTPUT_ROOT` 下的狀態目錄；`audit_log.json` 只能追加，agent 軌跡（source＝`agent_trace`）也在其中。網頁「Agent 軌跡」頁與軌跡 JSON 匯出在顯示前再遮一次（8 碼以上數字、電子郵件帳號），見 `koushi/agent_runs.py`。
- 學期切換先封存來源、主檔、文件與狀態，封存唯讀。正式環境的 ACL、加密與保存期限見[正式個資保護方案確認書](正式個資保護方案確認書.md)。

## 七、權限與人機協作

| 角色 | 能做的事 |
|---|---|
| 學生 | 填寫與補件自己的案件 |
| 委員 | 經一次性連結＋驗證碼回填自己的撥款資料 |
| 系辦專員 | 全部業務操作；所有修正、放行、核准都要填處理人與原因 |
| 評審 | 示範資料上的人機協作操作，可下載本輪產生的附件4／附件6（假資料）與遮蔽後的 agent 軌跡 JSON；不能改設定、上傳來源、匯出總表或下載封存（伺服器端白名單，見[評審模式](評審模式.md)） |
| 模型 | 只能提案；不能直接寫入任何狀態 |

自動執行的範圍（其餘一律待專員核准）：

- 教授回信判讀為無保留確認，且系辦已開啟自動確認、教授在白名單、關閉觀察模式（只記錄為已確認，不影響任何產檔或流程）。
- 信箱 agent 的固定範本「系辦已收到」通知（預設關閉、每人每天一封）。
- 學生來信的「記錄異動申請」（只記錄，不解鎖、不改狀態；疑似注入時降級為建議）。

**AI 總開關**：系辦在「AI 開關」頁可隨時停止所有模型呼叫與 agent 自動動作（須填處理人與原因，寫入稽核紀錄，所有頁面顯示紅色橫幅）；規則流程照常運作。

## 九、已知限制

- 回信引用清理對「底部回覆」與「無標記貼上原信」仍有已知漏洞（評測題組有標示）；這類信件轉人工。
- 離線備援是關鍵字規則替身，不是模型；展示若使用須揭露。
- 正式環境的 IMAP／SMTP、真實模型、ACL、加密與備份還原仍須校方驗收；本機測試不能代替。
- Gemini 免費額度有每分鐘／每日請求上限，大量信件或完整評測需付費額度或 OpenAI。
- 附件4 舊式 `.doc` 範本需 LibreOffice 轉檔。
- 問答助理「卡在哪一關」的判斷順序待系辦確認。
- 寄件者身分以 `From:` 地址比對，尚未檢查 DKIM／SPF（`Authentication-Results`）。附件4 自動確認另需白名單、本輪寄出信的同串回覆（含 8 碼代碼）、版本核對與無注入文字，且預設關閉；正式開啟自動確認前建議加上寄件網域驗證。
- 每日自動化的規則流程與信箱 agent 持有狀態鎖（含讀信與信箱 agent 的模型呼叫）；期間其他寫入操作會等待，逾時顯示「系統忙碌」頁、不執行該操作。提案型 agent 在釋放鎖之後才執行（寫入建議時才短暫上鎖），不會再拉長這段時間。展示控制台的「執行本日流程」本身是持鎖的網頁操作，展示時整輪都在鎖內。

## 十、故障排除

| 症狀 | 處理 |
|---|---|
| agent 全部顯示「轉人工」 | 檢查是否沒有設定任何 LLM 金鑰，或 AI 總開關／`KOUSHI_AI_DISABLED` 已停止（評審模式橫幅會標示目前模型） |
| 模型回 429 | 供應商額度用完；稍後重試或改用付費金鑰；信件已逐封轉人工，不會遺失 |
| 附件4 產檔失敗 | 確認 `resource/template/` 有範本，且 LibreOffice 可用（`KOUSHI_SOFFICE`） |
| 正式環境拒絕啟動 | `KOUSHI_ENV=production` 時必須設定機構識別與正式路徑，不得指向 mockdata |
| 每日流程提示「信箱 agent 本輪略過」 | 信箱 agent 出錯（例如資料檔損毀）；其他流程已完成，錯誤寫在稽核紀錄 `mailbox_agent/run_failed` |
| 每日流程提示「AI 建議（…）本輪略過」 | 該提案型 agent 出錯（例如距離表格式錯誤）；其他 agent 與流程照常，錯誤寫在稽核紀錄 `ai_proposals/run_failed`。下一輪會重試；也可到 AI 建議頁手動產生 |
| 排程漏跑告警 | 見[部署與上線操作手冊](部署與上線操作手冊.md) |
