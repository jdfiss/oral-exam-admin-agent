# 系辦問答助理設計（2026-10-08）

系辦人員在「問答助理」頁用一般問句查案件狀態，例如「哪些案件卡在待專員放行？」「附件4 已經寄給哪些教授？」。助理**只能讀資料**，不能寄信、放行、修改或登錄。

程式：`koushi/assistant.py`（流程與回答檢查）、`koushi/assistant_tools.py`（工具與代號化）、`koushi/llm.py`（模型介面）、`koushi/agent_trace.py`（執行軌跡）。網頁：`/office/assistant`。測試：`tests/test_assistant.py`（全部用假模型）。

## 為什麼這樣做能回應 LLM前置研究的疑慮

LLM前置研究 第二節不建議做「儀表板案件摘要」，理由是「狀態機已能精確說明卡在哪關，LLM 摘要反而可能說錯」。這個設計不讓模型判斷狀態，只讓它**挑工具、轉述結果**，並由程式檢查它有沒有說錯：

1. **狀態由程式算，不由模型算。** 卡在哪關、缺件、附件4 寄送、委員個資，全部來自工作總覽、人工關卡、文件中心、委員個資、通訊記錄頁**同一批函式**的結果（網頁層把 `_overview_rows`、`review_queue`、`tracking_snapshot` 的結果直接交給工具），所以助理查到的就是畫面上的資料。
2. **回答要通過程式檢查才會顯示**（`verify_answer`），任一項不符就整段作廢：
   - 回答必須列出引用的工具步驟（`sources`）；有提到案件、數字或狀態卻沒引用 → 作廢。
   - 每個案件代號都必須出現在引用的工具結果裡（編造的案件抓得到）。
   - 每個數字都必須出現在引用的工具結果、問題或今天日期裡（編造的件數抓得到）。
   - 句子提到案件又提到狀態詞時，那個狀態必須是工具結果中**該案件**的狀態（例如工具說「待專員放行」，模型說「已放行」→ 作廢）。狀態詞是封閉清單（關卡名稱與各頁的狀態標籤）。
   - 列舉型問題（「哪些案件卡在待專員放行？」「附件4 已經寄給哪些教授？」）列出的每個案件／人員，工具結果中的狀態必須是問題要的狀態；例如問待專員放行卻列出目前在「附件6尚未交付」的案件、問逾期卻列出「已寄出待回覆」的教授 → 作廢。問特定案件或句子是否定說法（「沒有…」「不是…」）時不做這項檢查。
   - 數字檢查不把文件名稱（附件2／附件4／附件6）裡的數字當成事實數字。
   - 回答聲稱「已幫您…」→ 作廢。
3. **作廢時不讓模型重講**，直接顯示原始工具結果表格，並標示「無法驗證，改顯示原始資料」，同時列出檢查不過的原因。
4. **每則回答都附查詢軌跡**（展開可看每一步的工具、輸入、輸出、耗時），軌跡也寫入稽核日誌，事後可追查。

檢查的限制（請知悉）：數字檢查只確認「這個數字存在於工具結果」，不保證它對應到正確的名詞（例如把「總案件 3 件」說成「逾期 3 件」不一定抓得到）。所以畫面一律附原始資料軌跡，重要決定仍以各頁面為準。

## 工具（全部唯讀）

| 工具 | 回答什麼 | 資料來源（與畫面同源） |
|---|---|---|
| `overview_counts` | 案件數、未填寫、附件2查無、待專員放行、學生補件逾期、各關卡案件數 | 工作總覽 |
| `list_cases(stage?, blocker?)` | 案件與目前卡住的關卡；可依「目前關卡」或「任一未通過關卡」篩選 | 工作總覽＋人工關卡＋缺件／附件4 寄送／附件6 追蹤 |
| `get_case(case)` | 單一案件：卡在哪關、全部未通過關卡、缺件、放行狀態與例外、附件4 寄送、委員個資（只有已回填／未回填）、附件6 | 案件詳情 |
| `list_confirmations(status?)` | 附件4 寄送紀錄（尚未寄出、已寄出、需修改、已確認；2026-10-12 起教授不用回信，沒有待回覆／逾期），教授回信待判讀件數 | 文件中心 |
| `list_deficiencies(owner?, status?)` | 缺件與例外，依責任別與狀態篩選 | 文件中心／案件詳情 |
| `list_source_issues()` | 尚未處理、沒有案件鍵的附件2 來源異常 | 來源異常頁 |
| `list_committee_data(missing_only?)` | 需要撥帳／身分資料的委員：已回填／未回填、是否已寄索取信、口試將至仍未回填 | 委員個資頁 |
| `get_deadlines()` | 本期學期、目前階段、填寫／補件截止日與各期限天數 | 期限設定 |
| `communication_counts(days?)` | 寄信件數（依類型與狀態），不含收件人與主旨 | 通訊記錄 |

關卡順序（「卡在哪關」＝第一個未通過的）：已撤銷 → 附件2查無 → 未填寫 → 等待附件2上傳 → 學生缺件 → 待專員放行 → 委員個資未齊 → 附件6尚未交付／待回收／需補正 → 流程完成。

## 個資

- 工具輸出**從不包含**身分證、金融機構、帳號、戶籍地址、E-mail；委員個資只回「已回填／未回填」。
- 依 LLM前置研究第七節「學校確認前，不把學生資料送雲端」：案件鍵、學號、學生姓名、教授與委員姓名，送給模型前一律換成代號（`CASE_01`、`STU_01`、`PER_01`），包括系辦問題裡打的字；剩下的 8 碼以上數字與 E-mail 再遮蔽。畫面顯示時才換回真實值，案件鍵做成可點開案件詳情的連結。
- 稽核軌跡只存代號化後的內容。

## 流程與限制

- 模型以 JSON 逐步選工具，最多 5 次；到上限仍要查就作廢、改顯示原始資料。
- 模型出錯（逾時、API 錯誤、格式錯誤）→ 顯示「暫時無法使用」，已查到的資料照樣列出。
- 要求「做事」的問題（寄信、放行、修改、登錄、上傳、改設定…）：明顯的由程式直接攔下、不呼叫模型；不明顯的由模型回報 `action_request`。兩者都回覆「只能查詢」並附上可以操作的頁面連結。助理本身沒有任何寫入工具，攔不到也做不了。
- 「（請）幫我把…改到…」「可以幫我把…延後嗎？」這類「祈使＋把／將＋寫入動詞」的句子，即使句尾有「嗎？」也視為要求做事，由程式直接拒絕；問題裡有案件（案件鍵、學號、姓名）時另附該案件詳情的連結。
- 規則／政策問題（口試費、交通費怎麼算、期限為什麼這樣訂）：工具裡沒有規則資料，交給模型只會變成猜測，所以由程式直接回覆「只查詢口試案件資料」，並指向期限設定、匯入資料（交通費歷史資料）與文件中心（附件6）。軌跡步驟為 `out_of_scope`。問日期（「補件截止日是哪天？」）仍是資料問題，照常查 `get_deadlines`。
- 離線備援模型（`koushi/offline_llm.py` 的 `assistant_step`）依常見問句挑工具與篩選參數：待放行 → `list_cases(blocker=待專員放行)`、附件4 寄給哪些教授 → `list_confirmations`、某學生的口試日期／附件4 寄送 → `get_case`、缺件 → `list_deficiencies`、委員資料 → `list_committee_data`、件數 → `overview_counts`；回答只用工具結果的欄位組句，查無資料就回「目前沒有…」。
- 問答請求不佔用狀態寫入鎖（等模型回應時不擋其他操作）。

## 設定

- 有設定 LLM（`GEMINI_API_KEY`，預設 gemini-3.5-flash-lite；或 `OPENAI_API_KEY`，可配 `OPENAI_BASE_URL`，預設 gpt-4o-mini；`KOUSHI_LLM_MODEL` 可覆寫）時，側欄出現「問答助理」，預設啟用；「期限設定」頁可關閉。
- 沒有設定 LLM 時，側欄與設定欄位都不顯示，頁面顯示停用原因。

## 稽核軌跡

每一步呼叫 `agent_trace.trace_step` 寫入 `audit_log.json`（source＝`agent_trace`，agent＝`assistant`，tracking_key＝本次問答編號）。步驟：`question`、`tool_call`、`grounding_check`（pass／repair／fail＋原因）、`reflect`、`refused`、`out_of_scope`、`llm_error`。欄位含模型、prompt 版本（`assistant-v1`）、耗時。用 `agent_trace.load_trace(state_dir, run_id=...)` 讀回。
